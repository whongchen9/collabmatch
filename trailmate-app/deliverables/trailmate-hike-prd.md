## 1. 产品目标

为 TrailMate 户外徒步组队 App 补全核心闭环——**从「组队聊天」走向「出发→征途→完成」**，让徒步不只是线上聊天，而是一场有始有终的户外体验。

| 目标 | 说明 |
|------|------|
| **体验闭环** | 队伍组建 → 出发确认 → 征途进行 → 凯旋完成 → 活动日志沉淀 |
| **仪式感** | 倒计时出发增强队伍同步感，打卡签到让每一步都有痕迹 |
| **安全感** | 征途中可随时 SOS、查看队友位置，关闭匹配避免干扰 |
| **成就感** | 到达终点后自动生成活动日志，记录里程/时长/照片/评分 |
| **流动性** | 队员退出后触发迭代匹配（找新队友），队伍可以动态重组 |

## 2. 用户故事

### US-1：队长出发仪式
> **作为队长**，我希望在出发时有 3-2-1 倒计时的仪式感，让自己和队员同步进入「征途」状态，不再担心被陌生匹配打扰。

**验收标准：**
- 队长点击「出发」按钮 → 若无打卡点，弹窗提示前往地图设置
- 若有打卡点 → 展示打卡点清单 → 点击「开始征途」→ 3-2-1 倒计时动画 → 自动进入 hiking 状态
- 进入 hiking 后，队伍匹配功能自动关闭，顶部显示绿色进度条横幅

### US-2：征途中打卡签到
> **作为队员**，我希望在徒步途中到达打卡点时能上传照片、写下此刻感受，而不仅仅是点一下按钮。

**验收标准：**
- 在地图页面点击打卡点小旗 → 签到弹窗：可输入备注 + 上传最多 3 张照片
- 签到成功后，打卡点标记显示签到人数
- 队伍聊天页进度条实时更新（已打卡数/总打卡点数）

### US-3：完成徒步与日志自动生成
> **作为队长**，我希望到达终点后一键「完成」，系统自动为每位队员生成一条活动日志作为纪念。

**验收标准：**
- 队长点击「完成」→ 展示征途摘要（打卡点/签到数/照片数）
- 确认完成 → 调用 `traillogsApi.generateFromGroup(groupId)` 为所有队员生成日志
- 日志自动填入：路线名称、日期、照片（从队伍相册继承）
- 完成后队伍状态变为 completed，显示「凯旋而归」横幅

### US-4：队员动态退出与迭代匹配
> **作为队员**，如果当前队伍不合适，我希望退出后能自动找到更合适的新队友，而不是停留在解散流程里。

**验收标准：**
- 队员点击「退出」→ 弹窗提示将触发迭代匹配 → 确认退出
- 退出后自动提取队伍聊天记录中的偏好分歧 → 追加新提示词 → 重新匹配
- 匹配结果引导前往首页查看（不自动创建新队伍）

### US-5：队长查看进度全景
> **作为队长**，我希望在征途 Banner 和完成弹窗中一眼看到队伍的签到进度和照片数量，掌握全队节奏。

**验收标准：**
- 征途 Banner 显示「征途中」标签 + 进度条 + 已打卡数/总打卡数
- 完成弹窗三栏摘要：打卡点数 / 已签到点数 / 队伍照片数
- 队长可在成员 Tab 查看谁签到了哪个打卡点（通过签到时间排序）

## 4. UI 交互说明

### 4.1 徒步全流程页面流转

```
[队伍聊天页 idle]
      │ 队长点击「出发」━━━ 无打卡点 ──→ 弹窗：引导去地图设置打卡点
      │                              └→ 跳转 LocationMap 页面
      │
      │ 队长点击「出发」━━━ 有打卡点 ──→ 弹窗：出发确认
      │     ├─ 展示打卡点编号+名称列表
      │     ├─ 点击「开始征途」
      │     ├─ 3-2-1 倒计时动画（每 800ms 切换）
      │     └─ 倒计时结束 → hikeStatus='hiking'

[队伍聊天页 hiking]
      ├─ 顶部绿色渐变横幅：🏔 征途中 · 1/5 打卡点
      └─ 进度条（白色填充，过渡动画 500ms）

      ├─ 「继续征途」→ 关闭弹窗，留在 hiking 状态
      └─ 「确定完成」→ hikeStatus='completed' → 自动生成日志

[队伍聊天页 completed]
      └─ 顶部琥珀色渐变横幅：🏁 凯旋而归 · 共计 N 个打卡点
```

**交互流程：**

2. 弹窗提示 → 确认退出
3. 离开队伍 `groupsApi.leave(id)` → 提取聊天记录 → `intentApi.dissolvePreview(intentId, chatMsgs)` → 提取偏好 → `intentApi.iterate(intentId, newPrompts)`
4. Toast：「已退出，正在寻找更合适的队友...」
5. 跳转至队伍列表 `/teams`

## 5. 数据模型变更

### 5.1 Group 模型（`src/types/index.ts`）

| 字段 | 类型 | 新增/修改 | 说明 |
|------|------|----------|------|
| `hikeStatus` | `'idle' \| 'hiking' \| 'completed'` | **新增** | 队伍徒步状态 |
| `matchingEnabled` | `boolean` | **新增** | 匹配开关，hiking 时强制 false |
| `checkpoints[].checkins[].photos` | `string[]` | **修改** | 签到照片 URL 数组（原只为标记签到，现在新增照片能力） |
| `checkpoints[].checkins[].notes` | `string` | **修改** | 签到备注（新增） |
| `checkpoints[].checkins[].checkedInAt` | `number` | **保留** | 签到时间戳 |
| `checkpoints[].checkins[].avatarColor` | `string` | **保留** | 签到成员头像颜色 |

**签到数据结构（完整）：**
```typescript
checkpoints: {
  lat: number;
  lng: number;
  label?: string;
  createdAt: number;
  checkins?: {
    userId: string;
    userName: string;
    avatarColor?: string;
    checkedInAt: number;
    photos?: string[];     // 新增
    notes?: string;         // 新增
  }[];
}[];
```

### 5.2 TrailLog 模型（无需变更）

当前模型已足够支持自动生成日志的需求：
- `groupId` — 关联源队伍
- `photos` — 从队伍相册继承
- `date` — 当前日期
- `title` — 使用队伍名称
- `location` — 使用打卡点坐标

**注意：** `generateFromGroup` 后端接口已存在（`traillogsApi.generateFromGroup(id)`），由后端负责为每个队员创建一条日志记录。

### 5.3 API 变更

| API | 方法 | 说明 |
|-----|------|------|
| `groupsApi.update(id, { hikeStatus })` | PUT | 更新队伍徒步状态 |
| `groupsApi.update(id, { matchingEnabled })` | PUT | 更新匹配开关 |
| `groupsApi.checkin(id, checkpointIndex, lat, lng)` | POST | 打卡签到（后端记录签到） |
| `traillogsApi.generateFromGroup(groupId)` | POST | 为全员生成活动日志 |
| `intentApi.iterate(intentId, additionalPrompts)` | POST | 迭代匹配（退出后重新匹配） |

## 6. 待确认问题

### Q1：打卡点距离校验策略
当前打卡签到要求距离打卡点 100 米内。但 GPS 在山区精度不足（误差可能 50-200 米），是否需要：
- A) 放宽至 200 米
- B) 队长可设置每个打卡点的签到半径
- C) 增加"强制签到"选项（队长/管理员旁路）

### Q2：征途中队长退出
当前逻辑：hiking 状态下列队长的「退出」按钮隐藏。如果队长确实需要退出（如意外离队），如何处理？
- A) 队长退出自动移交队长给时间最长的队员
- B) 队长退出 → 队伍自动解散（但征途日志已生成部分不丢失）

### Q3：完成条件
当前队长单方面点击「完成」即可结束。是否需要：
- A) 要求所有队员都签到过最后一个打卡点
- B) 多数队员签到后队长即可完成（如 ≥50%）
- C) 保持现状（队长单方面控制），但增加确认提醒

### Q4：日志自动生成时机
当前在队长点击「完成」时调用 `generateFromGroup`。如果：
- 队员 A 还没到终点就生成日志？
- 日志中的 distance/duration 如何计算（当前为空，需手动补填）？
- 是否需要完成后的「补填入口」引导队员补充里程和时长？

### Q5：迭代匹配的用户体验
当前退出后触发 `dissolvePreview` + `iterate`，但匹配结果需要用户去首页查看。是否需要：
- A) 退出后直接展示新匹配结果列表
- B) 发送通知 Push
- C) 保持现状，由用户自行查看

### Q6：旧 AI 解散 UI 残留
代码中 `intentApi.dissolvePreview` 和 `intentApi.dissolve` 仍然保留。虽然新 UI 不再使用解散流程，但后端 API 未变。确认：
- 是否彻底删除 `dissolve` 相关 API 调用？
- 还是保留兼容性，仅前端移除？

### Q7：非徒步类型队伍
队伍类型包含 `type: 'hike' | 'other'`。非徒步队伍是否也需要「出发→征途→完成」流程？
- 如果仅徒步需要，判定条件由前端控制即可
